# Loupe design rules

The normative base is the GPUI Kit Design Guides: `.claude/skills/gpui-kit-design-guides/references/design-guides.md`. Read it in full before designing or changing a screen, and run its Design review checklist before you finish. This file adds Loupe's own choices on top. The reasons behind them, and the diagnosis they answer, are in [design/redesign-plan.md](design/redesign-plan.md).

Loupe has Linear's structure, its own palette, and the kit's scale: dark, dense, quiet, with color only where it reports a state. Every screen follows these rules. A screen that breaks one is not done.

## Scale

- **The `rem` is 16 px** (`theme::BASE_FONT_SIZE`), gpui-component's default. Every GPUI scale helper then lands on a whole pixel of the 4 px grid, and stock components and Loupe's views share one set of sizes. Zoom multiplies it.
- **Layout uses the scale helpers** (`px_2`, `gap_3`, `h_8`, `size_4`) and `theme::scale`. A `px(…)` literal is allowed only for 1 px hairlines and window chrome that lines up with the system buttons. Sizes an API takes as `Pixels` (icons, avatars, fixed lanes) go through `scale::dp`, so they zoom.
- **Spacing is the kit's**: 2, 4, 8, 12, 16, 24, 32 px. Parts of one control are 4 px apart, related controls 8, lanes of a row 8 to 12, groups 16, sections 24.
- **One content edge.** Every bar, list, and body on a screen starts 16 px from the panel (`scale::content_inset`). A list whose rows have a hover fill pads its container 8 px and its rows 8 px, so labels sit on the edge and the fill reaches past it. Cards have 16 px of inner padding.

## Type

Inter for the interface and JetBrains Mono for code, both embedded (`assets::fonts`).

| Role | Size / line | Weight | Color |
|---|---|---|---|
| Heading (the title of an issue; a pull request's shares its line with the reference and is 18 / 26) | 22 / 28 | semibold | foreground |
| Title (page header, card and section titles) | 14 / 20 | semibold or medium | foreground |
| Body (list rows, the sidebar, values) | 13 / 20 | regular | foreground |
| Group title (a section of a list, a board column, a card) | 13 / 20 | semibold | foreground |
| Section label (a side column's section, a group of settings, the sidebar's groups) | 13 / 20 | semibold | muted (faint in the sidebar) |
| Controls (buttons, inputs, menus: gpui-component's `text_sm`) | 14 / 20 | regular | foreground |
| Prose (Markdown; 16 px between paragraphs) | 14 / 22 | regular | foreground |
| Meta (age, counts, identifiers, column labels) | 12 / 16 | regular | muted |
| Code (diffs, branches, SHAs, inline code) | 12 mono | regular | foreground |

- Sentence case everywhere. No uppercase labels.
- A fact that is always true of a screen (a read-only view) is a neutral chip beside the title (grey outline, muted text, a 12 px lock) with the reason in its tooltip, not a bar. Blue is for actions.
- A label that is a state and not a category ("Blocked") is a chip in the state's color with an icon, ahead of the categories.
- A row has one emphasis. Titles are regular weight; unread and selected use the foreground color, never bold; a selected row keeps its weight, so selecting it does not move its label.
- Monospace is for code, branch names, and SHAs. Issue identifiers and pull request numbers are names and use the interface font.
- All Markdown renders through `ui::markdown`: one reading style for pull request descriptions, comments, review threads, and Linear issues. A column of prose is at most `ui::READING_WIDTH` (760 px) wide. Markdown headings are 18, 16, 15, and 14 px. Inline code has 4 px of side padding on a fill of its own (`tokens::code_inline`), which stands off the panel and off a card.
- Lists never wrap a row title. Truncate it with an ellipsis. Where the end of a string is what tells two rows apart (a repository, a path, a file name), cut the head or the middle and keep the end, and put the whole string in a tooltip.

## Color

Use `cx.theme()` first and `theme::tokens` second. Never write a color in the code: every color is a token of a theme file (`crates/loupe-app/themes/*.json`, written by `scripts/make-themes.py`, or the user's under `<data dir>/themes/`), and `theme::fixed_colors` fails on a hex, `rgb`, `rgba`, or `hsla` literal anywhere in `src/`. Colors read from GitHub and Linear (labels, states, projects) are data and are the one exception (`theme::palette::data_color`).

A theme has a light and a dark palette with the same tokens. The values below are Loupe's dark palette, the default; its light palette and the other built-in themes (Grove, Ocean, Ember, Iris, Tokyo Night) keep the same roles and pass the same contrast rules, which `built_in_themes_pass_the_contrast_rules` checks. A new color role is a new token in every palette, never a value in a view.

- **Surfaces get lighter as they come forward:** the window and sidebar (`#0e0f11`), the content panel (`tokens::panel`, `#141518`), cards and inputs (`group_box`, `#1b1c20`), menus and dialogs (`popover`, `#212227`, with a shadow). On macOS the window is frosted glass and the first two are tints over it. A modal dialog dims the window under it (`tokens::scrim`, black at 55%) and is drawn on the `popover` surface, never on glass.
- **Borders:** `theme.border` (white 11%) outlines controls, cards, the panel, and overlays; `tokens::border_subtle` (white 6%) separates regions inside one surface.
- **Text:** foreground `#ecedf0`, muted `#a6a9b2`, faint `#8a8e99` (`tokens::text_faint`). Faint is 4.8:1 or more on every surface.
- **One accent**, the blue of the app icon (`tokens::accent`): focus rings, the unread dot, selection marks, and the icon of the open page in the sidebar. Blue is the filled action; green fills only Merge. The primary button's fill is that blue darkened until white text on it passes 4.5:1.
- **State colors** (open, merged, closed, draft, pending) appear only on state icons, state chips, check results, status letters, and the diff. A pull request's state on its own page is a solid pill with white text. A state never rests on color alone: its icon has its own shape (a pull request glyph per state, a person for a review, a circle for checks).
- **Hover and focus fill a row; selection in a menu is a check.** A fill never means two things. A menu opens under its trigger, its leading edge on the trigger's (its trailing edge for a trigger at the end of a bar), inside the content panel.

## Controls

Use gpui-component (`gpui_kit::component`) through the wrappers in `ui`. Do not rebuild these by hand.

| Control | Use | Size |
|---|---|---|
| `ui::icon_button` | toolbar and row actions with a well-known symbol; the name is its tooltip and accessible name | 24 px, 16 px icon |
| `Button` with `.control()` (`ui::ControlSize`) | labeled actions in a header or a form | 28 px |
| `Button` medium | the one commit of a decision area (Merge, Comment, Create) | 32 px |
| `ui::segmented` | a choice among two to four views of the same content | 30 px track with the control's one outline, 3 px inset, 24 px options with 13 px text and 10 px side padding; the selected option is a fill one step above the track |
| `ui::chip`, `ui::tinted_chip` | labels, states, decisions, relations: one token on every screen | 20 px, 12 px text, 8 px side padding, 10 px radius |
| `ui::count_badge` | every count beside a title, a tab, or a row | 18 px, 6 px side padding, 9 px radius, neutral fill |
| `ui::menu_row` | rows of the filter menus | 28 px, 12 px side padding |
| `ui::page_header`, `ui::toolbar` | the header row and the one bar under it | 44 px, 40 px |

- **Variants by meaning.** One filled button per decision area: Merge while the pull request can be merged, Review otherwise; Save in a form. Actions that would be an icon alone, and less used or destructive ones, go behind a "More actions" menu, where the destructive one is in the danger color. Other actions are outlined; quiet toolbar actions are ghost. A destructive action is outlined in the danger color and sits behind a confirmation.
- **Arrow cursor on controls and rows.** The pointing hand is for links that leave the app.
- Every interactive element has a role and an accessible name. A dropdown trigger uses `ui::MenuTriggerExt::menu_trigger` so accessibility clients can open it.
- Avatars are 20 px in rows, 16 px inline, 24 px for the account, with initials as the fallback.
- Loading uses `Skeleton` rows shaped like the final rows. Empty states are one muted line inside a section and an icon, a line, and an action for a whole screen. Errors are an inline alert with Retry.

## Frame

- **Top bar (40 px):** the sidebar toggle, back and forward for the active tab, the tabs (13 px text, 12 px side padding, 4 px apart, 128 to 220 px wide), and +. A row with more tabs than fit scrolls sideways with the trackpad or the wheel and keeps + in view after it; when the open tab changes, the row scrolls just enough to show it whole, and a tab opened in the background leaves the row where it is. It is a window drag area (`ui::WindowDragArea`). Only macOS reserves room for the traffic lights. A pending update is a 24 px neutral pill with a border and an accent dot at the bar's trailing edge, at least 12 px from the tabs.
- **Panes**, as in Zed and VS Code. A tab drags along its row to a new place (it takes the place of the tab it is dropped on; a 2 px accent line shows where), to another pane's row, or onto a page: within a quarter of the page from an edge the drop splits that pane and opens the tab on that side, in the middle it moves the tab into the pane, and the half or the whole page it lands on is washed in the accent with an accent outline while the tab is held. The lifted tab fades in its row. With one pane its tabs stay in the top bar; once the window is split, each pane has its own 36 px row of tabs over its page with a subtle bottom border, and the top bar keeps back, forward, and +, which act on the active pane (the one last pressed in). The active pane's open tab has the foreground color; the open tab of another pane keeps its fill with muted text. Panes are content cards 6 px apart; the gap is the divider, which drags (each side keeps at least 15%) and shares the space evenly on a double click. Closing a pane's last tab closes the pane and its neighbor takes the space. Split right, left, up, and down are in a tab's right-click menu (with Close tab), the Window menu, and the palette, on Cmd+\ and Cmd+Shift+\ for right and down; a tab that is its pane's only one opens again in the new pane, any other moves there. The panes, each split's share, and the tabs come back after a restart.
- **Tab groups**, as in Chrome. A tab's right-click menu has "Add to new group…" (a dialog asks for the name), "Add to group" with the pane's other groups, and "Remove from group". A group belongs to its pane and has a name and one of nine colors: Grey, Blue, Red, Yellow, Green, Purple, Pink, Cyan, Orange. Grey, Red, Yellow, Green, and Purple are the draft, closed, pending, open, and merged fills; Blue, Pink, Cyan, and Orange are tokens of their own (`group_blue`, `group_pink`, `group_cyan`, `group_orange`). Blue is a blue in every theme, the accent where the accent is blue. White text reads at 4.5:1 on each, and Pink, Cyan, and Orange stay apart from the other eight in every palette. A new group takes the first color no other group of the pane has. Its tabs sit next to each other after its name, a 22 px pill in its color with 12 px medium text, and carry a 2 px line of that color along their bottom edge. A click on the name collapses the group to the pill with the count of tabs it hides, and expands it again; the open tab is never hidden, so collapsing its group opens the nearest tab outside it (a group that holds every tab of its pane stays open), opening a hidden tab expands its group, and Ctrl+Tab skips hidden tabs. The name's right-click menu has Rename group…, Color (the current one checked), and Ungroup. A tab dragged onto a group's name joins it at its end, and onto a tab joins that tab's group; dropped on a tab outside every group, after the last tab, or on a page, it leaves its group. A tab opened from a grouped tab joins its group. A group with no tab left is gone. Groups, their colors, and which are collapsed come back after a restart.
- **Sidebar:** the workspace row, then Inbox, My issues, Reviews, then foldable sections. The workspace row is the workspace switcher, as in Linear (its name with a caret; O then W opens it from the keyboard): a menu of every connected Linear workspace under the email of the account it belongs to, the active one checked, then "Add a workspace…". Picking one reloads the sidebar, the views, and My issues from it; a page of the workspace left behind (a team, a project, an issue) gives way to My issues. Stars of another workspace's teams and issues are hidden. The workspace's mark is its logo from Linear, 20 px with a 5 px radius; its initial on the accent stands in only when the workspace has no logo. Rows are 28 px with 16 px icons. Collapsed to its rail (Cmd+B), it is the same sidebar with its texts hidden: the same rows in the same order, so every icon keeps its y, the step between rows, and the space between groups. At the top of the 72 px rail, the 44 px header row shows the workspace's mark alone, centered over the icons below, at the y it has with the sidebar open; the workspace's name is the mark's tooltip, and Search and New issue come back with the sidebar (Cmd+K still searches). A section's heading becomes a short divider in a slot of the same height, which still folds the section; the footer keeps the avatar and Settings on one row. A row on the rail has its label in a tooltip.
- **Content panel:** inset from the window edge, 12 px radius, 1 px border. Content fills its width; a list is not capped, prose is, and so are a form's cards (640 px). A connected account is one 80 px card: its state ("Signed in", "Connected") over the account on one line, the action centered on the card's height.
- **A screen has the header and at most one toolbar; a row of saved views that holds one or two sits in the header itself.** A row of filter chips appears only while a filter is set; each chip has its own × and the row ends in Clear. A team's toolbar holds its view tabs and, at the trailing edge, Filter, search, and Display. A team's tabs are Linear's views: its custom views, then the built-in Active, Backlog, and All issues. A change to a view is a draft, with "Unsaved changes", Discard, and Save at the trailing edge of the chip row; Save writes it to Linear, and on a built-in view "Save as new view…" makes a custom view there. A custom view whose filter Loupe cannot reproduce exactly keeps it as Linear has it: Filter then narrows the issues in the app, and a lock beside the title says why in its tooltip. The Views page lists Linear's views under one heading with fixed lanes (team 140 px, visibility 72 px, owner 160 px); the views still saved only in Loupe sit apart under "Only in Loupe", each with Save to Linear and Delete. Counts live in section headings, not in cards.
- **The Inbox's filter** is typed in a field at the toolbar's trailing edge: the command palette's `org:` and `repo:` prefixes, then free words. The word being typed filters at once; a finished one (a space after it, or Enter) leaves the field and becomes a chip beside Unread and All, and the whole chip is its remove button, with its ×. Clear follows the chips while a filter is set. A group's name narrows the Inbox to that repository. The filter is saved; the count beside Inbox, in the header and in the sidebar, is what the filter shows, and "Mark all as read" then marks only those, saying how many.
- **Detail pages** (a pull request, an issue) put the title in the content as the heading, where it can wrap, with the object's reference on the same line. Under the title, one 32 px band: what the object is (state, author, branches) at the leading edge, its actions at the trailing edge as 28 px outlined buttons 8 px apart (`ui::outline_icon_button` for the icon-only ones). A branch is a 20 px chip in the accent's wash with the link color. On that band the head branch is the one part that gives way: it ends in an ellipsis (its tooltip has it whole) while the state, the author, the size, and the checks keep their width, so nothing is drawn over anything else. In a window too narrow to show at least 96 px of the branch beside the actions, the actions go to a line of their own under the band. An issue's header is a breadcrumb: the team (one click back to its board), the identifier, the state as a chip with a caret that opens the state picker, and at the trailing edge the linked pull requests, the star, and Open in Linear. An issue's body is one reading column that scrolls as a whole: the title, the description, the linked pull requests right under it, the links, then the comments under their heading (with the real count, or "No comments yet"). Nothing is laid over it. The comment box stays at the foot of the column: one line while it is closed, an editor with the send hint and the Comment button once it has the focus or a draft. With nothing to send, the button is neutral with a readable label.
- **Settings** is a tab like every page (Cmd+,): one page of sections, in this order, General, Appearance, GitHub, Linear, T3 Code, Keyboard shortcuts, About, beside a 220 px nav that lists them under Preferences, Accounts, and Loupe. The nav marks the section being read as the sidebar marks the open page, and a click scrolls the page until that section sits where the first one starts. The header is a breadcrumb, "Settings / <section>", with that section's Restore defaults at its trailing edge, disabled while nothing differs from the defaults; accounts and watched repositories are the user's data and never a default. The nav's search field (/) narrows the page and the nav to the settings whose words start with the typed ones, and says so in one muted line when none does. A setting is one row: its name over a one-line description at the leading edge, its control at the trailing edge (a switch for on and off, `ui::segmented` for two options, a menu for more); the rows of one group share a card, with the group's name over it as a section label. Appearance holds the color scheme (System, Light, Dark: three thumbnails drawn in the current theme), the themes (a card per theme with its light and dark previews, Duplicate on every card, Edit and "More actions" with Export and Delete on the user's, Create theme and Add theme in the heading; a theme being added or edited opens under the cards, and every change repaints the app at once), Interface (Contrast and Glass opacity sliders, Density, Zoom, Sidebar width), and Typography (the interface and code fonts and sizes, each over a live preview: a row of text and a diff). T3 Code holds the server card, then the review request: the template a review thread starts with, the variables it can use listed under it, a line naming any `{word}` that is not one of them, and Restore default in its heading. Under it, the review prompts card, with Add prompt in its heading: one row per prompt in the dialog's order, its name with a Default or Risky pull requests chip, the model, effort, and provider it runs on under it (in red with the reason when the server cannot run it), and at the trailing edge move up, move down, edit (the pencil), and "More actions" with Make default, Use for risky pull requests, and Delete, which asks first and leaves the last prompt in place. The pencil opens the prompt's fields under its row: the name, the model selector (a searchable list of the models the connected T3 server reports, under each provider's name; only providers that can run threads), the effort the model offers, and the text, which goes where the template has `{prompt}`. Then Risky pull requests: a switch for the risk check, the prompt a risky pull request starts on, and the three lists (risk labels, risky path words, and the words that are not risky), each separated by commas and disabled while the switch is off. The review dialog has a tab per prompt and starts on the default one, or on the risk prompt for a risky pull request; under the tabs, the model the open tab runs on, or why the server cannot run it, with a warning on that tab and Send disabled. The dialog fills the template, and an edit there is for that one review. Keyboard shortcuts read their keys from the keymap, so the page lists only keys the app answers to. A sequence reads "O then W". Linear lists one account card per connected workspace (one personal API key each, from any of the user's accounts; the active one says so), a card with Remove for a saved key that stopped working, and the form that connects another. Its "Workspace by repository" maps a GitHub org or one repository to a workspace: a pull request's Linear issues come from its repository's workspace, else its owner's, else the active one, and an issue opened from there switches to its workspace first, as does a link to an issue of any connected workspace. With more than one workspace connected, the pull request's side column names the workspace beside "Linear issues".
- **One primary tone.** The filled accent button is the one commit of its area (Save, Comment, Approve, Finish review). Green is for the merge alone; red for a destructive commit behind a confirmation.
- **New issue** is a modal like Linear's, centered over the dimmed window, 720 px wide or the whole window (its full screen button): a breadcrumb with the team (a button that moves the issue to another team) and "New issue"; the title in the heading size and the description under it, both without a box; one row of property chips (Status, Priority, Assignee, Labels, Project, Cycle, Estimate, Due date; a team without cycles or estimates has no chip for them), each a 24 px outlined button with the value, or the property's name in the muted color, that opens a menu with a search field; a footer under a hairline with the last error or "Created ENG-12", the Create more switch, and Create issue. Closing it without creating keeps a draft until the app quits.
- **Keys.** A list with rows has a cursor: J and K (or the arrows) move it, Enter or O opens its row, Cmd+[ comes back. On an issue, S, P, A, and L open the state, priority, assignee, and labels pickers, where the arrows move and Enter picks, and C puts the caret in the comment box. F opens Filter on Reviews and on a team. C opens New issue. In New issue, Enter or Tab in the title goes to the description, Tab or Escape leaves the text, and then S, P, A, L, Shift+P, Shift+C, Shift+E, Shift+D, and T open the menus (typing narrows a menu, the arrows move, Enter picks); Cmd+Enter creates from anywhere in it, and Escape outside the text closes it. On Settings, / puts the caret in the search. Single-letter keys do nothing while a text field has the focus.
- Cells of one summary share one shape (icon, title, count, a 4 px bar of one width); where there is nothing to make progress on, the icon is a green check, the count says so in words, and the bar is its neutral track.
- **The merge box's Checks cell opens the list of checks**, as on GitHub: a chevron after its count, the list under the cells in sections by outcome (failing, pending, skipped, neutral, successful), each headed by its count ("2 failing checks") with a chevron that folds it. A row is the check's state icon, its workflow and name, what it did and how long it took ("Failing after 3m 5s"), Required, then Open in Actions and the details in the browser in fixed 24 px lanes. The list starts open while a check fails or runs and closed once every check settled well; a click keeps the user's choice while the pull request is open.
- **Side columns** are 296 px (360 px for an issue's properties, where a value sits beside its label) with a subtle left border. Every value of an issue's properties starts on one edge: a 16 px mark, then its text. A value that can be changed is a button with a caret at its trailing edge. Each section starts under a hairline. A section's action sits in its heading. An empty section says "None". A linked issue's card shows its title on up to three lines, 8 px from the line above and the line below, with the whole title in a tooltip.
- **A pull request's files** are a tree of the changed files beside the diff. The tree opens 340 px wide and its edge drags from 220 to 640 px. It is on the left, or on the right when Settings > File tree position says so; the toolbar mirrors with it, so the viewed count stays over the tree and the diff's controls over the diff. A file's header in the diff keeps its size, status, and Viewed at the trailing edge of the part of the diff on screen, whether lines wrap or scroll sideways. A path that does not fit loses its middle folders first, as in VS Code (`apps/…/service/billing.spec.ts`; the first folder and the ones nearest the file stay longest), then the end of the file name before its extension; the name is whole while it fits, the path grows back as the diff widens, and its tooltip and right-click Copy path have it whole.
- **View tabs** (`ui::view_tab`) are 32 px with 12 px of side padding and one active state. A row shows up to six views, as many as its width holds whole; the rest go under "More". The open view is always in the row. On Reviews, the saved views' tabs scroll sideways with the trackpad or the wheel instead when the header cannot hold them, and the open view scrolls just enough to show it whole when it changes; Save as new view, the view's menu, Filter, Sort, "Unsaved changes", Discard, and Save follow the row and never scroll or shrink.
- **A board scrolls sideways** with the trackpad, Shift + wheel, or a card dragged to within 72 px of a side; a sideways gesture never scrolls a column and a vertical one never scrolls the board. Its scrollbar shows while it scrolls, and a side with columns past it fades into the panel. A column with no card is as narrow as its heading and stays a place to drop a card. A column's heading drags the column to another place: it takes the place of the column it is dropped on, a 2 px accent line between two columns shows where it lands, and the column it left fades while it moves. Its "…" menu also moves it left or right and hides it; Display shows the hidden columns again and resets the order. The order and the hidden columns belong to the view, like its other display settings: Save keeps them in Linear (`columnOrderBoard`, `hiddenColumns`).

## Rows and cards

- A list whose rows have more than three lanes has one 24 px heading over each section's rows, starting at the rows' own leading edge, with a 12 px label per lane. The trailing lanes (repository 150 px, changes 90 px right-aligned, comments, checks, age) keep their widths and their x in every section, so one grid runs down the list; a lane a section has no use for (the author of your own pull requests) is dropped and the title takes its width. A fact most rows lack gets no lane: a review decision is a chip right after the title, on the rows that have one. A number ends 12 px before its title. The hairline between rows starts and ends on the content's edge. An empty cell is a faint dash.
- **Sorting Reviews.** Every lane's label but the title's is a button: a click sorts by that column (ascending, then descending, then GitHub's order), and the sorted column's label takes the foreground color with a 12 px arrow before it; its tooltip says what the next click does. "Sort" beside Filter lists the same fields plus Created, which the Age lane then counts from, with the two directions in words ("Largest first") and Default order. One sort applies to every section, and each section sorts its own rows. Rows without a value (no checks, a deleted author) go last both ways; ties keep GitHub's order. Like a filter, a sort is a change to the view: "Unsaved changes" until Save keeps it with the view.
- **Picking pull requests on Reviews.** A 16 px checkbox lane leads every row, 12 px before the state icon; the column labels start after it, and the section heading's lane holds a box that picks or drops the whole section. A box shows while its row or heading is hovered, and every box shows once anything is picked. A click on the box picks the row; Shift+click, on the box or the row, picks the range from the last click in the order on screen; Cmd+A picks the section of the keyboard cursor, or else of the last click; Escape or the bar's × drops the selection. While rows are picked, a toolbar over the list says how many ("3 selected") and offers outlined actions: Open in new tabs (background tabs, in list order), Open on GitHub, Copy links (one per line, in list order), and Mark as read (the pull requests' unread GitHub notifications, with the result at the trailing edge, before ×). The list scrolls by the bar's height as it comes and goes, so no row moves under the pointer (a list too short to scroll moves once). The header keeps Filter, Sort, and the views. Opening more than 10 asks in the bar first ("Open 14 pull requests in new tabs?", Cancel, Open 14). A new sort keeps the selection; a change to the filters or to the view drops it.
- **A row's menu.** A right click on a row or a card that stands for an issue or a pull request (My issues, a team's list and board, the Inbox, Reviews, a repository) opens one menu, as Linear's, with a 16 px icon on every row and its key at the trailing edge: Open, Open in new tab, Open side by side; for an issue, Status, Priority, Assignee, Labels, and Project as submenus with the current value checked, then Copy link, Copy ID, Copy title, Copy branch name, and Open in Linear; for a pull request, Copy link, Copy branch, Copy title, Open on GitHub, and Open in T3 Code when a T3 thread is linked to it. A GitHub issue in the Inbox has Open on GitHub, Copy link, and Copy title. The keys act on the row under the pointer, or else on the page on screen: S, P, A, L, and Shift+P open that property's list in the palette, Cmd+Enter opens in a new tab, Cmd+Shift+Enter side by side, Cmd+Shift+, copies the link, Cmd+. the ID, Cmd+Shift+. the branch. The palette lists the same commands first, under the item's reference, for the same item. A change shows on every screen at once and comes back, with a notification, if Linear refuses it; a copy says in a notification what it copied.
- List rows are 32 px (44 px with a second line): a 16 px state icon, the identifier, the title, then fixed lanes on the right. Indicators get 24 px lanes that stay in place when empty, so they form columns down the list. Ages end on the header's right edge.
- Rows that read the same stack into one 32 px row with two glyphs: a chevron at the leading edge (under the group heading's) and the unread dot; then, in words, what happened and where ("CI failed · feat/x"), how many it holds, and when the latest came; the age in a 40 px column at the trailing edge. A stack starts closed; the whole row opens and closes it. A row inside a stack says only what sets it apart (the run's number and outcome, the jobs that failed, the exact time) and never repeats the stack's line. A single row has its kind's icon where a stack has its chevron. A failed workflow run names its pull request (number and title, read from GitHub by the branch), then "CI failed" beside a red mark and the jobs that failed, and has an Open PR button; the blue dot means unread and nothing else.
- Board cards have 12 px of padding and blocks always in this order, 4 px apart: identification (state, identifier, assignee), the title (three 19 px lines at most), one line of pills in a fixed order (priority, Blocked, linked pull request with the whole number, labels, project), then a footer in the faint color (the date, then cycle, estimate, due date). The priority, Blocked, and the pull request are never hidden; the categories after them go behind "+N", with their names in its tooltip, when the line is short. The pills are 4 px apart and the "+N" is never cut: what would not fit goes behind it. An empty block is not drawn. A board or a diff that runs past the right edge fades into the panel there, and while a diff's long lines scroll, its toolbar says how many files have them, beside the Scroll and Wrap control: on a dark surface a fade alone says nothing.

## Don't

- Duplicate a title or a count.
- Put a box around rows that sit in a panel, or a card inside a card.
- Use a fill, a color, or bold for two meanings on one screen.
- Leave an interactive element under 24 px, without a name, or reachable only on hover.
- Write developer text in the product ("TODO", "stub").
