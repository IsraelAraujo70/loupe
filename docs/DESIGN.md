# Loupe design rules

The normative base is the GPUI Kit Design Guides: `.claude/skills/gpui-kit-design-guides/references/design-guides.md`. Read it in full before designing or changing a screen, and run its Design review checklist before you finish. This file adds Loupe's own choices on top. The reasons behind them, and the diagnosis they answer, are in [design/redesign-plan.md](design/redesign-plan.md).

Loupe has Linear's structure, its own palette, and the kit's scale: dark, dense, quiet, with color only where it reports a state. Every screen follows these rules. A screen that breaks one is not done.

## Scale

- **The `rem` is 16 px** (`theme::BASE_FONT_SIZE`), gpui-component's default. Every GPUI scale helper then lands on a whole pixel of the 4 px grid, and stock components and Loupe's views share one set of sizes. Zoom multiplies it.
- **Layout uses the scale helpers** (`px_2`, `gap_3`, `h_8`, `size_4`) and `theme::scale`. A numeric `px(…)` literal over 2 px is forbidden in screen code (`theme::fixed_sizes` enforces this in CI, exempting `theme.rs`, `main.rs`, `ui.rs`, and the OS window-chrome files `shell/tab_bar.rs`, `shell/sidebar.rs`, `shell/mod.rs`) and allowed elsewhere only for 0/0.5/1/2 px hairlines/offsets. Sizes an API takes as `Pixels` (icons, avatars, dialogs, popovers, fixed lanes) go through `theme::scale` tokens (`icon_xs`/`sm`/`md`, `avatar_xs`/`sm`/`md`, `search_width`, `dialog_sm`, `popover_width`, `menu_min_width`, `pill_radius`, `dp`), so they zoom with the window.
- **Spacing is the kit's**: 2, 4, 8, 12, 16, 24, 32 px. Parts of one control are 4 px apart, related controls 8, lanes of a row 8 to 12, groups 16, sections 24.
- **One content edge.** Every bar, list, and body on a screen starts 16 px from the panel (`scale::content_inset`). A list whose rows have a hover fill pads its container 8 px and its rows 8 px, so labels sit on the edge and the fill reaches past it. Cards have 16 px of inner padding.

## Type

Inter for the interface and JetBrains Mono for code, both embedded (`assets::fonts`).

| Role | Size / line | Weight | Color |
|---|---|---|---|
| Heading (the title of an issue; a pull request's shares its line with the reference and is 18 / 26) | 22 / 28 | semibold | foreground |
| Title (page header, card and section titles) | 14 / 20 | semibold or medium | foreground |
| Body (list rows, the sidebar, values) | 13 / 20 | regular | foreground |
| Group title (a section of a list, a board column, a card) | 13 / 20 | semibold | foreground |
| Section label (a side column's section, a group of settings, the sidebar's groups) | 13 / 20 | semibold | muted (faint in the sidebar) |
| Controls (buttons, inputs, menus: gpui-component's `text_sm`) | 14 / 20 | regular | foreground |
| Prose (Markdown; 16 px between paragraphs) | 14 / 22 | regular | foreground |
| Meta (age, counts, identifiers, column labels) | 12 / 16 | regular | muted |
| Code (diffs, branches, SHAs, inline code) | 12 mono | regular | foreground |

- Sentence case everywhere. No uppercase labels.
- A fact that is always true of a screen (a read-only view) is a neutral chip beside the title (grey outline, muted text, a 12 px lock) with the reason in its tooltip, not a bar. Blue is for actions.
- A label that is a state and not a category ("Blocked") is a chip in the state's color with an icon, ahead of the categories.
- A row has one emphasis. Titles are regular weight; unread and selected use the foreground color, never bold; a selected row keeps its weight, so selecting it does not move its label.
- Monospace is for code, branch names, and SHAs. Issue identifiers and pull request numbers are names and use the interface font.
- All Markdown renders through `ui::markdown`: one reading style for pull request descriptions, comments, review threads, and Linear issues. A column of prose is at most `ui::READING_WIDTH` (760 px) wide. Markdown headings are 18, 16, 15, and 14 px. Inline code has 4 px of side padding on a fill of its own (`tokens::code_inline`), which stands off the panel and off a card.
- Lists never wrap a row title. Truncate it with an ellipsis. Where the end of a string is what tells two rows apart (a repository, a path, a file name), cut the head or the middle and keep the end, and put the whole string in a tooltip.

## Color

Use `cx.theme()` first and `theme::tokens` second. Never write a color in the code: every color is a token of a theme file (`crates/loupe-app/themes/*.json`, written by `scripts/make-themes.py`, or the user's under `<data dir>/themes/`), and `theme::fixed_colors` fails on a hex, `rgb`, `rgba`, or `hsla` literal anywhere in `src/`. Colors read from GitHub and Linear (labels, states, projects) are data and are the one exception (`theme::palette::data_color`).

A theme has a light and a dark palette with the same tokens. The values below are Loupe's dark palette, the default; its light palette and the other built-in themes (Grove, Ocean, Ember, Iris, Tokyo Night) keep the same roles and pass the same contrast rules, which `built_in_themes_pass_the_contrast_rules` checks. A new color role is a new token in every palette, never a value in a view.

- **Surfaces get lighter as they come forward:** the window and sidebar (`#0e0f11`), the content panel (`tokens::panel`, `#141518`), cards and inputs (`group_box`, `#1b1c20`), menus and dialogs (`popover`, `#212227`, with a shadow). On macOS the window is frosted glass and the first two are tints over it. A modal dialog dims the window under it (`tokens::scrim`, black at 55%) and is drawn on the `popover` surface, never on glass.
- **Borders:** `theme.border` (white 11%) outlines controls, cards, the panel, and overlays; `tokens::border_subtle` (white 6%) separates regions inside one surface.
- **Text:** foreground `#ecedf0`, muted `#a6a9b2`, faint `#8a8e99` (`tokens::text_faint`). Faint is 4.8:1 or more on every surface.
- **One accent**, the blue of the app icon (`tokens::accent`): focus rings, the unread dot, selection marks, and the icon of the open page in the sidebar. Blue is the filled action; green fills only Merge. The primary button's fill is that blue darkened until white text on it passes 4.5:1.
- **State colors** (open, merged, closed, draft, pending) appear only on state icons, state chips, check results, status letters, and the diff. A pull request's state on its own page is a solid pill with white text. A state never rests on color alone: its icon has its own shape (a pull request glyph per state, a person for a review, a circle for checks).
- **Hover and focus fill a row; selection in a menu is a check.** A fill never means two things. The row under a list's keyboard cursor (J and K or the arrows, then Enter: Reviews, the Inbox, My issues, a team's list, a repository's pull requests, Actions, a pull request's checks, and Projects) also has a 1 px accent ring inside its edge while the list has the focus (`ui::ListRowFocus`), so keyboard focus never reads as hover or as a picked row, and it is the accessibility focus too. No leading-edge bar. The first key puts the cursor on the first row, as in Linear. A menu opens under its trigger, its leading edge on the trigger's (its trailing edge for a trigger at the end of a bar), inside the content panel.

## Controls

Use gpui-component (`gpui_kit::component`) through the wrappers in `ui`. Do not rebuild these by hand.

| Control | Use | Size |
|---|---|---|
| `ui::icon_button` | toolbar, header, and row utility actions with a well-known symbol (ghost); the name is its tooltip and accessible name | 24 px, 16 px icon |
| `ui::outline_icon_button` | icon-only menu trigger sitting beside 28 px outlined controls in a detail header (`More actions`) | 28 px square |
| `Button` with `.control()` (`ui::ControlSize`) | labeled actions in a header or a form; a quiet utility link (`Open on GitHub`) uses ghost, primary area action uses primary/outline | 28 px (`scale::control_height`) |
| `Button` medium | the one commit of a decision area (Merge, Comment, Create) | 32 px |
| `ui::segmented` | a choice among two to four views of the same content (e.g. Unread/All, Open/Closed/Merged/All) | 30 px track with the control's one outline, 3 px inset, 24 px options with 13 px text and 10 px side padding; the selected option is a fill one step above the track |
| `ui::chip`, `ui::tinted_chip`, `ui::branch_chip`, `ui::status_chip` | labels, states, decisions, relations, Git branches, and metadata status chips: one token on every screen | 20 px (`scale::chip_height`), 12 px text (`scale::code` mono for branches), full pill or `theme.radius` |
| `ui::count_badge`, `ui::accent_badge` | every count beside a title, a tab, or a row (neutral or emphasized accent) | 18 px (`scale::badge_height`), 6 px side padding, `scale::pill_radius` |
| `ui::menu_row` | rows of the filter menus | 28 px, 12 px side padding |
| `ui::page_header`, `ui::toolbar`, `ui::meta_band`, `ui::notice_bar`, `ui::vertical_divider` | page header, action/filter bar, detail metadata band, inline dismissible error strip, and 1 px control-group divider | 44 px, 40 px, 36 px min (`scale::band_height`), inset to `scale::content_inset` |
| `ui::section_tabs` (`ui::section_tab`) | horizontal underline section tabs under a header or band (PR tabs, Reviews tabs, Repository tabs) | 40 px (`scale::toolbar_height`), 2 px bottom accent indicator, optional icon, `count_badge`, and trailing slot |
| `ui::list_container`, `ui::list_row`, `ui::list_row_divider`, `ui::list_column_header`, `ui::list_group_header`, `ui::nav_row` | vertical lists, collapsible groups, multi-lane column headers, row hairlines, and secondary side navs | 8 px container inset (`p_2`), 32 px density-aware rows (`scale::row_height`), 24 px column headings (`scale::column_header_height`), 28 px nav rows (`scale::nav_row_height`) |
| `ui::side_panel`, `ui::side_section`, `ui::side_sections`, `ui::side_empty` | leading or trailing fixed-width side columns (`SideEdge::Leading` / `SideEdge::Trailing`) and hairline-separated sections | `scale::side_width` (296 px), `scale::side_wide_width` (360 px), `scale::nav_width` (220 px for Settings nav and Actions Run jobs); 24 px section rhythm with subtle hairline halfway |
| `ui::empty_state`, `ui::empty_line`, `ui::loading_rows`, `ui::load_error` | whole-screen empty state, inline section empty line, skeleton list rows inside `p_2`, and inset error banner with Retry | full-panel centered / inline muted / 32 px skeleton rows / `content_inset` banner |

- **Variants by meaning.** One filled button per decision area: Merge while the pull request can be merged, Review otherwise; Save in a form. Actions that would be an icon alone, and less used or destructive ones, go behind a "More actions" menu, where the destructive one is in the danger color. Other actions are outlined; quiet toolbar actions are ghost. A destructive action is outlined in the danger color and sits behind a confirmation.
- **Arrow cursor on controls and rows.** The pointing hand is for links that leave the app.
- Every interactive element has a role and an accessible name. A dropdown trigger uses `ui::MenuTriggerExt::menu_trigger` so accessibility clients can open it.
- Avatars are 20 px in rows, 16 px inline, 24 px for the account, with initials as the fallback.
- Loading uses `Skeleton` rows shaped like the final rows. Empty states are one muted line inside a section and an icon, a line, and an action for a whole screen. Errors are an inline alert with Retry.

## Frame

- **Top bar (40 px):** the sidebar toggle, back and forward for the active tab, the tabs (13 px text, 12 px side padding, 4 px apart, 128 to 220 px wide), and +. A pull request's tab reads `#592 repo`, the number first and the repository without its owner; when the tab is narrow the repository is cut, never the number. Its tooltip is `owner/repo#592` over the pull request's title, and a 12 px mark after the name shows your review while no commit has landed after it: a green check for an approval, a red cross for a change request. The palette's tab search matches the number, the repository, and the title. A row with more tabs than fit scrolls sideways with the trackpad or the wheel and keeps + in view after it; when the open tab changes, the row scrolls just enough to show it whole, and a tab opened in the background leaves the row where it is. It is a window drag area (`ui::WindowDragArea`). Only macOS reserves room for the traffic lights. A pending update is a 24 px neutral pill with a border and an accent dot at the bar's trailing edge, at least 12 px from the tabs.
- **Panes**, as in Zed and VS Code. A tab drags along its row to a new place (it takes the place of the tab it is dropped on; a 2 px accent line shows where), to another pane's row, or onto a page: within a quarter of the page from an edge the drop splits that pane and opens the tab on that side, in the middle it moves the tab into the pane, and the half or the whole page it lands on is washed in the accent with an accent outline while the tab is held. The lifted tab fades in its row. With one pane its tabs stay in the top bar; once the window is split, each pane has its own 36 px row of tabs over its page with a subtle bottom border, and the top bar keeps back, forward, and +, which act on the active pane (the one last pressed in). The active pane's open tab has the foreground color; the open tab of another pane keeps its fill with muted text. Panes are content cards 6 px apart; the gap is the divider, which drags (each side keeps at least 15%) and shares the space evenly on a double click. Closing a pane's last tab closes the pane and its neighbor takes the space. Split right, left, up, and down are in a tab's right-click menu (with Close tab), the Window menu, and the palette, on Cmd+\ and Cmd+Shift+\ for right and down; a tab that is its pane's only one opens again in the new pane, any other moves there. The panes, each split's share, and the tabs come back after a restart.
- **Tab groups**, as in Chrome. A tab's right-click menu has "Add to new group…" (a dialog asks for the name and offers the nine colors as 24 px swatches, the first free one checked), "Add to group" with the pane's other groups, and "Remove from group". A group belongs to its pane and has a name and one of nine colors: Grey, Blue, Red, Yellow, Green, Purple, Pink, Cyan, Orange. Grey, Red, Yellow, Green, and Purple are the draft, closed, pending, open, and merged fills; Blue, Pink, Cyan, and Orange are tokens of their own (`group_blue`, `group_pink`, `group_cyan`, `group_orange`). Blue is a blue in every theme, the accent where the accent is blue. White text reads at 4.5:1 on each, and Pink, Cyan, and Orange stay apart from the other eight in every palette. A new group takes the first color no other group of the pane has. Its tabs sit next to each other after its name, a 22 px pill in its color with 12 px medium text, and carry a 2 px line of that color along their bottom edge. A click on the name collapses the group to the pill with the count of tabs it hides, and expands it again; the open tab is never hidden, so collapsing its group opens the nearest tab outside it (a group that holds every tab of its pane stays open), opening a hidden tab expands its group, and Ctrl+Tab skips hidden tabs. The name's right-click menu has Rename group…, Color (the current one checked), Ungroup, and Close group, which closes every tab of the group at once and keeps it: its name, color, tabs (the page each showed), and place. A right click on + lists the closed groups, the latest first and at most 10, each as "Reopen group <name>" after a dot of its color; reopening brings the group back with the same name, color, and tabs, in the active pane where it was (at the end when that place is gone), and takes it off the list, which comes back after a restart. A plain click on + still opens a new tab. The name drags the whole group, open or collapsed, its tabs in order: it takes the place of the tab, or the whole group, it is dropped on, with the tab's 2 px accent line where it lands, and never lands inside another group or among the pinned tabs. A tab dragged onto a group's name joins it at its end, and onto a tab joins that tab's group; dropped on a tab outside every group, after the last tab, or on a page, it leaves its group. A tab opened from a grouped tab joins its group. A group kept in sync with a saved Reviews view shows a 12 px sync icon before its name, and its name's menu has Stop syncing, which makes it a plain group; closing it and reopening it gives back a plain group. A group with no tab left is gone. Groups, their colors, and which are collapsed come back after a restart.
- **Pinned tabs**, as in Chrome. A tab's right-click menu has "Pin tab" (and "Unpin tab" on a pinned one), after the splits. Pinned tabs come first in their pane's row, in the order they were pinned; a pinned tab is as wide as its icon and name (a repository without its owner), up to 112 px, has no close button (Close tab stays in its menu, and Cmd+W and a middle click still close it), and its whole name is its tooltip. A pinned tab keeps its page: a pull request, an issue, a link, or a sidebar row opened from it opens in a new tab right after the pinned tabs, and Cmd+click still opens one in the background; a change of the page's own filter that goes through its route (the branch of a repository's runs, a team's view) stays in the pinned tab. Unpinning puts the tab right after the pinned ones. A pinned tab is never in a group: "Add to new group…", "Add to group", or a drop on a group's name unpins it, and pinning a grouped tab takes it out of its group. A tab dragged along the row stays on its side: an unpinned one stops after the pinned tabs, a pinned one at their end, and a tab on the other side shows no landing line. Pinned tabs come back after a restart.
- **Sidebar:** the workspace row, then Inbox, My issues, Reviews, then foldable sections. The workspace row is the workspace switcher, as in Linear (its name with a caret; O then W opens it from the keyboard): a menu of every connected Linear workspace under the email of the account it belongs to, the active one checked, then "Add a workspace…". Picking one reloads the sidebar, the views, and My issues from it; a page of the workspace left behind (a team, a project, an issue) gives way to My issues. Stars of another workspace's teams and issues are hidden. The workspace's mark is its logo from Linear, 20 px with a 5 px radius; its initial on the accent stands in only when the workspace has no logo. Rows are 28 px with 16 px icons. A star in Favorites shows what it is, with its page's icon in the faint color (a box for a project, a cycle's arrows, a dot for an issue); only a custom view keeps the icon and color picked for it in Linear. A team's row starts folded, except the team of the open page (its board, projects, views, or one of its issues); once the user opens or folds a team, it stays so. Collapsed to its rail (Cmd+B), it is the same sidebar with its texts hidden: the same rows in the same order, so every icon keeps its y, the step between rows, and the space between groups. At the top of the 72 px rail, the 44 px header row shows the workspace's mark alone, centered over the icons below, at the y it has with the sidebar open; the workspace's name is the mark's tooltip, and Search and New issue come back with the sidebar (Cmd+K still searches). A section's heading becomes a short divider in a slot of the same height, which still folds the section; the footer keeps the avatar and Settings on one row. A row on the rail has its label in a tooltip. A window narrower than 1100 px shows the rail whatever the setting, so the page keeps room to read, as a pull request's details column starts behind Details below 1600 px; Cmd+B or the top bar's toggle opens the sidebar for as long as the window stays narrow, and Settings keeps only the wide window's choice. The sidebar is a navigation landmark named "Sidebar".
- **The sidebar's Repositories** list the pinned repositories, then the watched ones, both in the order the user gave them, then those of the open pull requests that involve you (the Reviews page's, read every 10 minutes) by name; a repository shows once. The section starts with Actions, the runs of every listed repository newest first, with menus for repository, workflow, branch, and status (the workflow, branch, and status menus offer what the chosen repository's runs have). A repository's row is its owner's avatar and its name, with a 12 px pin when pinned; a click folds or opens it, as a team's, and open it holds Pull requests and Actions. Its right-click menu has Pull requests, Actions, Pin to top or Unpin, and, for a pinned or watched one, Move up, Move down, and Remove from sidebar, then Open on GitHub. A pinned or watched row drags onto another of its own part of the list and takes its place. A repository's page has the header with the full name and, under it, the `ui::section_tabs` Pull requests and Actions, the open one with its count; each tab is its own route, and switching stays in a pinned tab. Its Open pull requests read as a review queue: under a 32 px heading per group (a chevron that folds it, the name, its count), Review requested, Changes since your review, Not reviewed, Yours, Reviewed, then Draft, each in GitHub’s order, with no heading when every row falls in one group. Review requested, Changes since your review, and Reviewed come whole from a search of their own on the repository (`review-requested:@me`, and `reviewed-by:@me` for those you reviewed), so a pull request that waits on you shows on the first screen even when its page is not loaded yet, where its last update falls. While pages are left, the other groups count only what is loaded: the count reads "28+", and its tooltip and the heading's accessible name say it is the loaded ones. Load more keeps the row being read at the same place on screen while the new rows join their groups. Pull requests that build on each other (GitHub’s stack, else a chain of branches where exactly one loaded pull request has the base as its head and only one builds on it) are one stack row in the group of the most urgent of them, which opens base first, in merge order, as on Reviews (a click or Enter, Right and Left). Closed, Merged, and All keep GitHub’s order, ungrouped. The palette finds a repository and, when the query has words, "Actions of owner/name" right after it; "actions" in the query keeps only the Actions rows.
- **Content panel:** inset from the window edge, 12 px radius, 1 px border. Content fills its width; a list is not capped, prose is, and so are a form's cards (640 px). A connected account is one 80 px card: its state ("Signed in", "Connected") over the account on one line, the action centered on the card's height.
- **A screen has the header and at most one toolbar; a row of saved views that holds one or two sits in the header itself.** A row of filter chips appears only while a filter is set; each chip has its own × and the row ends in Clear. A team's toolbar holds its view tabs and, at the trailing edge, Filter, search, and Display. A team's tabs are Linear's views: its custom views, then the built-in Active, Backlog, and All issues. A change to a view is a draft, with "Unsaved changes", Discard, and Save at the trailing edge of the chip row; Save writes it to Linear, and on a built-in view "Save as new view…" makes a custom view there. A custom view whose filter Loupe cannot reproduce exactly keeps it as Linear has it: Filter then narrows the issues in the app, and a lock beside the title says why in its tooltip. The Views page lists Linear's views under one heading with fixed lanes (team 140 px, visibility 72 px, owner 160 px); the views still saved only in Loupe sit apart under "Only in Loupe", each with Save to Linear and Delete. Counts live in section headings, not in cards.
- **The Inbox's filter** is typed in a field at the toolbar's trailing edge: the command palette's `org:` and `repo:` prefixes, then free words. The word being typed filters at once; a finished one (a space after it, or Enter) leaves the field and becomes a chip beside Unread and All, and the whole chip is its remove button, with its ×. Clear follows the chips while a filter is set. A group's name narrows the Inbox to that repository. An empty Inbox says whether the filter is what hides the rest: with no notification at all it says so "with or without the filter", and with some it says how many unread ones the filter leaves out; its actions are Show read (while only the unread show) and Clear filter (while one is set). The filter is saved; the count beside Inbox, in the header and in the sidebar, is what the filter shows, and "Mark all as read" then marks only those, saying how many.
- **The command palette** (Cmd+K) is a 620 px dialog: the field ("Search or run a command…"), the list, and a footer of keys. While the field is empty, a line under it offers the prefixes that narrow the list (`pr:`, `repo:`, `org:`, `issue:`, `tab:`, or a team key) as chips that type themselves in. Every row of the list, a group's heading too, is 32 px, and the list shows 12 of them before it scrolls, so it never ends in the middle of a row.
- **Detail pages** (a pull request, an issue) put the title in the content as the heading, with the object's reference on the same line. A pull request's header is 72 px and never wraps, so its tabs end at most 112 px under the top of the page, whatever the window: one 28 px line with the title (cut with an ellipsis, whole in its tooltip), the reference, and at the trailing edge the actions as 28 px buttons 8 px apart (`ui::outline_icon_button` for the icon-only ones); under it the 20 px meta line with what the pull request is (state, author, branches, size, checks). The title comes before the labeled actions and the reference: when the line cannot hold the whole title and reference beside every action, Open on GitHub and then Summarize move to the top of "More actions", over a separator, while the review button (or Merge) and "More actions" stay. Only then does the reference give way, the repository first (cut, then hidden) while the number stays, and the title is cut last. On a pull request, Review changes is the one filled action while Merge is not offered and outlined once it is; a merged or closed pull request has none, unless a pending review is left to finish. Copy link is in "More actions". A branch is a 20 px chip in the accent's wash with the link color. On the meta line the head branch is the one part that gives way: it ends in an ellipsis (its tooltip has it whole) while the state, the author, the size, and the checks keep their width, so nothing is drawn over anything else. An issue's header is a breadcrumb: the team (one click back to its board), the identifier, the state as a chip with a caret that opens the state picker, and at the trailing edge the linked pull requests, the star, and Open in Linear. An issue's body is one reading column that scrolls as a whole: the title, the description, the linked pull requests right under it, the links, then the comments under their heading (with the real count, or "No comments yet"). Nothing is laid over it. The comment box stays at the foot of the column, under a hairline, and the column fades out over its last 16 px above it, so a comment cut there reads as going on: one line while it is closed, an editor with the send hint and the Comment button once it has the focus or a draft. With nothing to send, the button is neutral with a readable label (`ui::send_button`), and the send key is a key cap beside it (`ui::send_hint`), as in a pull request's comment box.
- **Settings** is a tab like every page (Cmd+,): one page of sections, in this order, General, Appearance, GitHub, Linear, T3 Code, Keyboard shortcuts, About, beside a 220 px nav that lists them under Preferences, Accounts, and Loupe. The nav marks the section being read as the sidebar marks the open page, and a click scrolls the page until that section sits where the first one starts. The header is a breadcrumb, "Settings / <section>", with that section's Restore defaults at its trailing edge, disabled while nothing differs from the defaults; accounts and watched repositories are the user's data and never a default. The nav's search field (/) narrows the page and the nav to the settings whose words start with the typed ones, and says so in one muted line when none does. A setting is one row: its name over a one-line description at the leading edge, its control at the trailing edge (a switch for on and off, `ui::segmented` for two options, a menu for more); the rows of one group share a card, with the group's name over it as a section label. Appearance holds the color scheme (System, Light, Dark: three thumbnails drawn in the current theme), the themes (a card per theme with its light and dark previews, Duplicate on every card, Edit and "More actions" with Export and Delete on the user's, Create theme and Add theme in the heading; a theme being added or edited opens under the cards, and every change repaints the app at once), Interface (Contrast and Glass opacity sliders, Density, Zoom, Sidebar width), and Typography (the interface and code fonts and sizes, each over a live preview: a row of text and a diff). T3 Code holds the server card, then the review request: the template a review thread starts with, the variables it can use listed under it, a line naming any `{word}` that is not one of them, and Restore default in its heading. Under it, the review prompts card, with Add prompt in its heading: one row per prompt in the dialog's order, its name with a Default or Risky pull requests chip, the model, effort, and provider it runs on under it (in red with the reason when the server cannot run it), and at the trailing edge move up, move down, edit (the pencil), and "More actions" with Make default, Use for risky pull requests, and Delete, which asks first and leaves the last prompt in place. The pencil opens the prompt's fields under its row: the name, the model selector (a searchable list of the models the connected T3 server reports, under each provider's name; only providers that can run threads), the effort the model offers, and the text, which goes where the template has `{prompt}`. Then Risky pull requests: a switch for the risk check, the prompt a risky pull request starts on, and the three lists (risk labels, risky path words, and the words that are not risky), each separated by commas and disabled while the switch is off. The review dialog has a tab per prompt and starts on the default one, or on the risk prompt for a risky pull request; under the tabs, the model the open tab runs on, or why the server cannot run it, with a warning on that tab and Send disabled. The dialog fills the template, and an edit there is for that one review. Review with T3 Code on several picked pull requests opens one dialog: the same tabs and model line, the template with the picked prompt's text and its variables still unfilled (an edit there is for every pull request of that round), and the list of the pull requests in the order on screen, each with its repository, number, and title over where its thread will run (branch and project, a warning with the reasons for a risky one) or why it is skipped, in the words the single button uses (a fork, a repository no T3 project tracks, your own pull request, one GitHub did not load). It starts on the risk prompt when any ready pull request is risky. Start N reviews starts one thread per ready pull request, each in its own worktree on its own branch; each row then says Started or Failed with the reason, a failure stops none of the others, and Retry sends the failed ones again under the same request ids. Keyboard shortcuts read their keys from the keymap, so the page lists only keys the app answers to. A sequence reads "O then W". Linear lists one account card per connected workspace (one personal API key each, from any of the user's accounts; the active one says so), a card with Remove for a saved key that stopped working, and the form that connects another. Its "Workspace by repository" maps a GitHub org or one repository to a workspace: a pull request's Linear issues come from its repository's workspace, else its owner's, else the active one, and an issue opened from there switches to its workspace first, as does a link to an issue of any connected workspace. With more than one workspace connected, the pull request's side column names the workspace beside "Linear issues".
- **One primary tone.** The filled accent button is the one commit of its area (Save, Comment, Approve, Finish review). Green is for the merge alone; red for a destructive commit behind a confirmation.
- **New issue** is a modal like Linear's, centered over the dimmed window, 720 px wide or the whole window (its full screen button): a breadcrumb with the team (a button that moves the issue to another team) and "New issue"; the title in the heading size and the description under it, both without a box; one row of property chips (Status, Priority, Assignee, Labels, Project, Cycle, Estimate, Due date; a team without cycles or estimates has no chip for them), each a 24 px outlined button with the value, or the property's name in the muted color, that opens a menu with a search field; a footer under a hairline with the last error or "Created ENG-12", the Create more switch, and Create issue. Closing it without creating keeps a draft until the app quits.
- **Keys.** A list with rows has a cursor: J and K (or the arrows) move it, Enter or O opens its row, Cmd+[ comes back. On an issue, S, P, A, and L open the state, priority, assignee, and labels pickers, where the arrows move and Enter picks, and C puts the caret in the comment box. F opens Filter on Reviews and on a team. C opens New issue. In New issue, Enter or Tab in the title goes to the description, Tab there goes on to the property chips, Create more, and Create issue (Shift+Tab comes back), Escape leaves the text, and outside the text S, P, A, L, Shift+P, Shift+C, Shift+E, Shift+D, and T open the menus, as Enter or Space on a chip does (typing narrows a menu, the arrows move, Enter picks, and Escape or a pick closes it with the focus back on its chip); Cmd+Enter creates from anywhere in it, and Escape outside the text closes it. On Settings, / puts the caret in the search. Single-letter keys do nothing while a text field has the focus.
- **Focus and Tab.** Tab and Shift+Tab walk the window in the order it reads: the top bar, the sidebar's rows (the workspace switcher, Search, New issue, each section's heading and row, the footer), then each pane, its row of tabs, its page's header, and last the page's list (`shell::page_focus`). A sidebar row or heading in the Tab order (`ui::TabStopRow`) opens or folds with Enter or Space and draws `ui::ListRowFocus`'s ring while it holds the focus, and scrolls into view when Tab reaches it out of sight; a click on it leaves the focus where it was, as a button's does. A page that comes on screen in the active pane (a link, Back or Forward, another tab, the palette) takes the keyboard focus (a pull request's page holds it itself on the tabs without a list of their own: Conversation, Guide, and Commits), so its keys work at once and an overlay that closes never leaves the focus on a control of the window.
- Cells of one summary share one shape (icon, title, count, a 4 px bar of one width); the icon becomes a green check only once every item is done. Nothing to count (no checks, no review threads, no reviewers) is not a success: the icon stays neutral, the count says so in words, and the bar is its neutral track. On an open pull request nobody was asked to review, a viewer who may change it gets "Request review" in place of the count, a link to the pull request on GitHub, where reviewers are picked.
- **The merge box's Checks cell opens the list of checks**, as on GitHub: a chevron after its count, the list under the cells in sections by outcome (failing, pending, skipped, neutral, successful), each headed by its count ("2 failing checks") with a chevron that folds it. A row is the check's state icon, its name as GitHub's merge box writes it ("CI / check (pull_request)": the workflow, the job, and the event, so the push and pull request runs of one job read apart), what it did and how long it took ("Failing after 3m 5s"), Required, then the details in the browser in a fixed 24 px lane. A click on the row opens the check's run in Loupe on its own job, whether the check is queued, running, or done (an Actions check GitHub names no run for opens the branch's workflow runs; a commit status has no page in Loupe). The list ends in "View workflow runs", the runs of the pull request's branch. The list starts open while a check fails or runs and closed once every check settled well; a click keeps the user's choice while the pull request is open.
- **One check per job.** A job that ran again in a later run of its workflow for the same event (the commit pushed again, a label that starts the workflow) counts and shows only its latest run, and a re-run shows its latest attempt. A commit status a job posts about its own run (its name, linking to that run) is the same check: one row, with the status's description and the worse of the two outcomes. Every count of checks (the tab, the header, the merge box) counts these checks.
- **The Checks tab** groups the checks as GitHub's checks page does: one group per workflow and event, by name, then "Other checks" (commit statuses and other apps' checks). A group's heading is a 32 px button with a chevron that folds it, the workflow's name, the event in the meta style ("on push"), and its count; its rows give the job's name alone. A row opens its run in Loupe like the merge box's, and ends in its duration and the details in the browser.
- **A workflow run** reads as GitHub's run page. The header holds the title, the workflow and number, and the actions (Re-run with all or failed jobs, Cancel run behind a confirmation, the workflow file, the browser, Refresh). Under it, one band of blocks, each a 12 px label over its value: "Triggered via pull request 4m ago" over the actor, the branch, and the short SHA; Status, in the state's color with its icon; Total duration; Artifacts; Attempt after a re-run. The jobs column (220 px) has Summary, then the jobs under All, Failing, and Running (`ui::segmented`): a matrix or a called workflow is one group with a chevron, its state as one, and "n/m" ended, its jobs indented under it; jobs and groups go running (queued after running), then failing (failed, cancelled), then the rest, in the graph's order otherwise. The graph runs left to right, one column per step of `needs`, with a curve from each box to the boxes that need it; a matrix folds to "Matrix: <key>" over "n/m jobs completed", which opens on a click (and on its own while it holds the open job). Every name cut short has its whole text in a tooltip. Annotations group by job, worst first, each message once with a "×3" badge when the job left it more than once; the job's name opens its log. While the run goes, its times tick every second and it reloads every 5 s; GitHub serves a job's log only once the job ends, so a running job shows its steps live and its log the moment it finishes.
- **Merging a stacked pull request** merges the open pull requests under it too, so its confirmation says how many merge and into which branch ("This merges 3 pull requests into release with squash:") and lists them under the question, base first and this one last: one 28 px row each with the state icon, the number (12 px, ending on the edge of a 40 px lane, as in a list row), the title, red chips for Conflicts and Changes requested, and the checks in a 128 px lane at the trailing edge, red when they fail. A pull request outside a stack, or with nothing open under it, keeps the one-line confirmation.
- **Side columns** are 296 px (360 px for an issue's properties, where a value sits beside its label) with a subtle left border. A pull request's details column (its Linear issues, then Reviewers, Labels, and Assignees, then its T3 threads) folds with Details at the trailing edge of the tabs (`Hide details` / `Show details`): it starts open in a window 1600 px wide or more and hidden in a narrower one, and keeps the user's choice for each of the two widths across pull requests and restarts. Its Reviewers, Labels, and Assignees are one block of properties, a row each with the name in an 88 px lane and the values after it ("None" when there are none), so an empty one takes a line and not a section; the label editor's gear ends its row. An integration that is not connected takes no section: one line closes the column with which ones ("Linear, T3 not connected") and Settings, which opens the first of them. The Files tab has no details column. Every value of an issue's properties starts on one edge: a 16 px mark, then its text. A value that can be changed is a button with a caret at its trailing edge. Each section starts under a hairline. A section's action sits in its heading. An empty section says "None". A linked issue's card shows its title on up to three lines, 8 px from the line above and the line below, with the whole title in a tooltip.
- **A pull request's files** are a tree of the changed files beside the diff. The tree opens 340 px wide and its edge drags from 220 to 640 px. It is on the left, or on the right when Settings > File tree position says so; the toolbar mirrors with it, so the viewed count stays over the tree and the diff's controls over the diff. A file's header in the diff keeps its size, status, and Viewed at the trailing edge of the part of the diff on screen, whether lines wrap or scroll sideways. A path that does not fit loses its middle folders first, as in VS Code (`apps/…/service/billing.spec.ts`; the first folder and the ones nearest the file stay longest), then the end of the file name before its extension; the name is whole while it fits, the path grows back as the diff widens, and its tooltip and right-click Copy path have it whole. Between two hunks of a changed file, above its first and below its last, a band on the hunk rows' fill offers what GitHub's Expand arrows do: Expand down under a hunk and Expand up over one, 20 lines each, and the whole run with its count ("42 unchanged lines"), or that one control alone when the run is 20 lines or fewer. The first use reads the file at the commit the diff shows, in the whole pull request and in one commit alike. Revealed lines are searched like the rest; GitHub takes comments only on the patch's own lines, so a new comment on one says so.
- **Diffs GitHub leaves out.** A file whose diff GitHub left out of a large pull request or commit opens folded, with its note and Load diff. The toolbar counts them ("69 diffs not loaded") beside an outlined Load all, and the find bar offers the same Load all beside "69 files not searched": the search does not load them on its own, since opening it is cheap and loading them costs one call for the merge base and one or two per file. Load all reads four files at a time, asks for no more while GitHub's rate limit is under a tenth, shows "Loading diffs: 22 of 69" with a spinner in both bars and Stop in the toolbar, and puts every diff in the viewer at once when the last arrives, keeping the file at the top where it is; a run that stops early says why beside Load all. The diff always opens on the first file's header, whatever is folded.
- **Find in the diff** (Ctrl+F, Cmd+F on macOS) counts every place the text appears ("3 of 41"), in a line or in the scope a hunk's `@@` header names, and marks the text itself in the warning color; only the current match's line is also marked whole. Going to the previous or next commit keeps the bar open with its text and goes to that commit's first match.
- **A pull request's guide** fills the panel up to the side column, as the Files tab does: its cards, its decision and walkthrough rows, and its diff snippets take the whole width, so a wide window shows more of the code, not an empty band. Only its prose stops at `ui::READING_WIDTH`: the Markdown of the summary and the steps, a decision's impact, a removed test's reason, and the summary's bullets. A snippet's long lines wrap or scroll sideways as the Files tab's Scroll and Wrap control says, and while they scroll the snippet's trailing edge fades as the Files diff's does.
- **A commit's changes.** A click on a row of the Commits tab shows that commit's changes against its first parent in the Files tab, with the same tree, diff, and Load diff, under a bar: All changes (back to the whole pull request), the commit's SHA and headline, its place ("3 of 12"), the previous and next commit, and Open on GitHub. Each row also keeps an Open on GitHub button. Viewed marks there are the pull request's, as on GitHub, but a viewed file stays open, since the commit may change it again; threads and new comments belong to the whole diff and are not shown.
- **View tabs** (`ui::view_tab`) are 32 px with 12 px of side padding and one active state. A row shows up to six views, as many as its width holds whole; the rest go under "More". The open view is always in the row. On Reviews, the saved views' tabs scroll sideways with the trackpad or the wheel instead when the header cannot hold them, and the open view scrolls just enough to show it whole when it changes; Save as new view, the view's menu, Filter, Sort, "Unsaved changes", Discard, and Save follow the row and never scroll or shrink. A Reviews page's header and its tab are named after the open saved view, and "Reviews" on All; a switch, a rename, or a deletion renames them at once.
- **The bell of a saved view.** Each saved view on Reviews has a bell, as on YouTube: a 24 px icon button right after its tab (a faint bell while off, a ringing bell on the selected fill while on) and "Notify about new pull requests", checked while on, in the view's menu. It starts off. While it is on, a pull request that comes into the view's All tab (a new one, or one that starts to match its filters) raises a system notification: the pull request's title over `owner/repo#N · <view>`; a click opens it in Loupe and brings the window forward. A pull request is announced once, even if it leaves the view and comes back; what the view lists when the bell is turned on, or when the app starts, announces nothing. The tab counts the announced pull requests not seen yet in a filled accent badge after its name, until the view opens. The views are watched whether a Reviews page shows them or not, at the pace of a page behind another window (the one-point question every 3 min, a full load every 30 min). Settings > General > Mute notifications silences the notifications; the counts stay.
- **A board scrolls sideways** with the trackpad, Shift + wheel, or a card dragged to within 72 px of a side; a sideways gesture never scrolls a column and a vertical one never scrolls the board. Its scrollbar shows while it scrolls, and a side with columns past it fades into the panel. A column with no card is as narrow as its heading and stays a place to drop a card. A column's heading drags the column to another place: it takes the place of the column it is dropped on, a 2 px accent line between two columns shows where it lands, and the column it left fades while it moves. Its "…" menu also moves it left or right and hides it; Display shows the hidden columns again and resets the order. The order and the hidden columns belong to the view, like its other display settings: Save keeps them in Linear (`columnOrderBoard`, `hiddenColumns`).

## Rows and cards

- A list whose rows have more than three lanes has one 24 px heading over each section's rows (over the open tab's on Reviews), starting at the rows' own leading edge, with a 12 px label per lane. The trailing lanes (repository 150 px, size 90 px right-aligned, comments, checks, age) keep their widths and their x in every section, so one grid runs down the list; a lane the list has no use for is dropped and the title takes its width: the author of your own pull requests, the repository when every row comes from one, the comments when no row has any. The author lane (140 px) is the 20 px avatar and the login after it, cut at the lane's end. A tab whose rows all fall in one group shows them without the group's heading, since it sets nothing apart. With no saved view, Reviews has no "All" view tab beside its title: it would repeat the All tab. A fact most rows lack gets no lane: a review decision is a chip right after the title, on the rows that have one, and it always shows, the title giving way to it. After it, an open pull request says what it asks of you, as a chip with its icon: Review requested (pending, an eye), Changes since your review (accent, a commit: your latest review is on an older commit than the head), Reviewed (neutral, a check: your latest review is on the head), or Draft (the draft color); your own pull requests and those you have no part in have none, and a pending review of yours counts as none. With one of these, "Review required" is left out. The state chip takes only the room the title leaves: it shows whole or not at all, so it never cuts the title, and under a heading that already names its state (the repository's grouped Open list) it is left out. The row’s accessible name says the state, the decision, and the size ("…, changes since your review, changes requested, size S"). A number ends 12 px before its title. The hairline between rows starts and ends on the content's edge. An empty cell is a faint dash.
- **Size, not raw +/−.** The size lane is a meter of four 2 px bars, one per class, filled up to the pull request’s, then the class, in the foreground color for XL. The class counts the lines changed (additions plus deletions): S under 100, M under 500, L under 2,000, XL from 2,000 (`loupe_github::queue::SizeClass`). The tooltip has the class, its range, and the lines added and removed ("Size XL, 2,000 lines changed or more · +78,029 −0"). A stack’s row sizes its rows added up.
- **Reviews' tabs and groups.** Under the header (and the filter chips), a `ui::section_tabs` strip holds the tabs Needs review, Mine, Involved, and All, each an underline tab with its count under the filters (`ui::count_badge`, 0 for an empty tab), and the open tab's note ("Showing 50 of 120") in its trailing slot. All lists once every pull request whose review is asked of you (`review-requested:@me`), of Mine, and of Involved, and on a view that names repositories every other open one in them. Needs review lists those of All that are open, not drafts, and not approved, and that are yours, asked of you (yourself or through a team), or that nobody was asked to review and nobody but their author reviewed (bots do not count); one asked of someone else stays in All. Its count is the sum of its groups. The page opens on the first tab with pull requests, in that order, unless the saved view keeps another. One column heading over the open tab's rows sits outside the scroll. Inside Needs review the rows group, in this order, as Requested from you, No reviewer, and Yours (your own pull request goes to Yours, even when nobody was asked). Inside every other tab the rows group by their next step, in this order, each pull request in the first group whose rule it meets: Ready to merge (approved, no check failing or running, no conflict, not a draft), Checks failing, Changes requested, Waiting for review (any other pull request that is not a draft), Draft. A group with no rows is not shown. Its 32 px heading is a button on the rows' grid: the checkbox lane, a 16 px chevron over the state icons (down open, right folded), the group title, and its count; a click folds it in every tab. The open tab and the folded groups save with the view at once, without "Unsaved changes", since they are where the user is rather than a change to what the view shows. An empty tab is one muted line.
- **Stacks on Reviews.** Pull requests that build on each other read as one row in their group: GitHub's stack where it has one, else the chain of branches, where a pull request is stacked on the open one whose head branch is its base when GitHub counts it as the only open pull request on that branch (never by its title; a long-lived branch such as `staging`, or one two pull requests build on, ends the chain). The row has the checkbox lane, a chevron over the state icons (right folded, down open), a 16 px stack mark in the number lane, the name (the title of the pull request at its base), then a neutral chip before the name that says how many it holds ("Stack · 3", or "Stack · 3 of 10" when the filters or the tab leave out part of it), and after the name, in the meta style, how many fail their checks ("2 checks failing", or "1 check running" when none fails); the accessible name keeps "3 PRs · 2 checks failing"; its lanes add up its rows (the author when they share one, the repository, the size and comments summed, the worst checks, the latest age). A stack starts folded; a click, Enter, or the arrows (Right opens, Left folds, from its row or one inside) open and fold it. Open, its rows follow base first, 16 px further in past a 1 px line under the chevron that links them, each with its place ("2/4") after the title. A stack goes whole to the group of its most urgent row, at the place the sort gives its first row. Its box picks every row of it the tab shows, and Shift+click on the box or the row extends the selection over the whole stack; a folded stack's rows are on screen through its row, so Cmd+A and a Shift+click range take them. A stack with one row in the tab is a plain row. Group and tab counts count pull requests.
- **Sorting Reviews.** Every lane's label but the title's is a button: a click sorts by that column (ascending, then descending, then GitHub's order), and the sorted column's label takes the foreground color with a 12 px arrow before it; its tooltip says what the next click does. "Sort" beside Filter lists the same fields plus Created, which the Age lane then counts from, with the two directions in words ("Largest first") and Default order. One sort applies to every tab, and each group sorts its own rows. Rows without a value (no checks, a deleted author) go last both ways; ties keep GitHub's order. Like a filter, a sort is a change to the view: "Unsaved changes" until Save keeps it with the view.
- **Picking pull requests on Reviews.** A 16 px checkbox lane leads every row, 12 px before the state icon; the column labels start after it, and a group heading's lane holds a box that picks or drops the whole group (a folded group has none). A box shows while its row or heading is hovered, and every box shows once anything is picked. A click on the box picks the row; Shift+click, on the box or the row, picks the range from the last click in the order on screen; Cmd+A picks every row the open tab shows (a folded group's rows are not on screen and leave the selection); Escape or the bar's × drops the selection. While rows are picked, a toolbar over the list says how many ("3 selected") and offers outlined actions: Open in new tabs (background tabs, in list order), Open in group, Open on GitHub, Copy links (one per line, in list order), Mark as read (the pull requests' unread GitHub notifications, with the result at the trailing edge, before ×), and Review with T3 Code (disabled, with the reason, while T3 is not connected). The list scrolls by the bar's height as it comes and goes, so no row moves under the pointer (a list too short to scroll moves once). The header keeps Filter, Sort, and the views. Open in group is a menu: New group… (the dialog of "Add to new group…"), "Open as group <view>" while a saved view is open and every row on screen is picked, with "Keep in sync with the view" under it while the view has no unsaved changes and its rows have loaded (a box, off until ticked and again after each use, that leaves the menu open), then the active pane's groups, each with a dot of its color. A group kept in sync follows every pull request of the open tab under the view's saved filters, folded groups included, from the list as it stood when the group opened: every two minutes, and whenever Reviews loads or the view's filters are saved, a pull request new to that list opens in the group as a background tab, and the group's tab of one that left it (merged, closed, or out of the filters) closes. No pane's open tab is closed or switched by a sync; a tab closed or taken out of the group by hand stays so; a failed load changes nothing, and a list GitHub sent only part of opens what is new and closes nothing. Deleting the view stops the sync and keeps the group. The pull requests open in background tabs, in list order, at the end of the group; one already open in a tab, in any pane, moves that tab into the group instead of opening a second one, and one already in the group stays where it is. A new group starts right after the open tab. Opening more than 10 asks in the bar first ("Open 14 pull requests in new tabs?", "… in group Review?", Cancel, Open 14), before a new group's dialog. A new sort keeps the selection; a change to the filters, to the view, or to the tab drops it.
- **A row's menu.** A right click on a row or a card that stands for an issue or a pull request (My issues, a team's list and board, the Inbox, Reviews, a repository) opens one menu, as Linear's, with a 16 px icon on every row and its key at the trailing edge: Open, Open in new tab, Open side by side; for an issue, Status, Priority, Assignee, Labels, and Project as submenus with the current value checked, then Copy link, Copy ID, Copy title, Copy branch name, and Open in Linear; for a pull request, Copy link, Copy branch, Copy title, Open on GitHub, and Open in T3 Code when a T3 thread is linked to it. A GitHub issue in the Inbox has Open on GitHub, Copy link, and Copy title. The keys act on the row under the pointer, or else on the page on screen: S, P, A, L, and Shift+P open that property's list in the palette, Cmd+Enter opens in a new tab, Cmd+Shift+Enter side by side, Cmd+Shift+, copies the link, Cmd+. the ID, Cmd+Shift+. the branch. The palette lists the same commands first, under the item's reference, for the same item. A change shows on every screen at once and comes back, with a notification, if Linear refuses it; a copy says in a notification what it copied.
- List rows are 32 px (44 px with a second line): a 16 px state icon, the identifier, the title, then fixed lanes on the right. Indicators get 24 px lanes that stay in place when empty, so they form columns down the list. Ages end on the header's right edge.
- Rows that read the same stack into one 32 px row with two glyphs: a chevron at the leading edge (under the group heading's) and the unread dot; then, in words, what happened and where ("CI failed · feat/x"), how many it holds, and when the latest came; the age in a 40 px column at the trailing edge. A stack starts closed; the whole row opens and closes it. A row inside a stack says only what sets it apart (the run's number and outcome, the jobs that failed, the exact time) and never repeats the stack's line. A single row has its kind's icon where a stack has its chevron. A failed workflow run names its pull request (number and title, read from GitHub by the branch), then "CI failed" beside a red mark, the jobs that failed, and the branch in the meta style, and has an Open PR button; without a pull request, "CI failed" leads the line. Why GitHub sent a notification ("Review requested", "Mentioned") is a neutral chip right after its title, not a column at the far edge; a run says it in its own words and has none. The unread dot is 8 px; it means unread and nothing else.
- Board cards have 12 px of padding and blocks always in this order, 4 px apart: identification (state, identifier, assignee), the title (three 19 px lines at most), one line of pills in a fixed order (priority, Blocked, linked pull request with the whole number, labels, project), then a footer in the faint color (the date, then cycle, estimate, due date). The priority, Blocked, and the pull request are never hidden; the categories after them go behind "+N", with their names in its tooltip, when the line is short. The pills are 4 px apart and the "+N" is never cut: what would not fit goes behind it. An empty block is not drawn. A board or a diff that runs past the right edge fades into the panel there, and while a diff's long lines scroll, its toolbar says how many files have them, beside the Scroll and Wrap control: on a dark surface a fade alone says nothing.

## Don't

- Duplicate a title or a count.
- Put a box around rows that sit in a panel, or a card inside a card.
- Use a fill, a color, or bold for two meanings on one screen.
- Leave an interactive element under 24 px, without a name, or reachable only on hover.
- Write developer text in the product ("TODO", "stub").
